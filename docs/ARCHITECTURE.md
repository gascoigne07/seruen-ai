# Архитектура Seruen AI

Streamlit и CLI используют один конвейер `seruen.cli.advise()`. База POI хранится на сервере
приложения в JSON. При запуске на компьютере владельца этот компьютер и является сервером. Для поиска используются геометрия, жёсткие фильтры и BM25. Векторная база не нужна.

## Поток запроса

1. Старт поступает из ручного выбора либо определяется из текста. В режиме OpenAI
   `origin_resolution.py` сначала выделяет точное упоминание текущего места с помощью
   модели. JSON проверяется: модель не возвращает координаты, а фраза должна реально
   присутствовать в запросе. После этого имя проверяется по локальному каталогу,
   проверенным ориентирам и при необходимости Photon. Неоднозначный результат требует
   подтверждения, неизвестный — уточнения. Отсутствующий старт не заменяется Байтереком.
2. `intent.py` извлекает бюджет, язык, категории и требования. Для OpenAI и локального
   режима предпочтения разбираются в Python; Gemini дополнительно умеет модельный intent.
   Контекст восстанавливается из исходного запроса удалением только проверенного
   упоминания старта, а не переписыванием модели. Кафе возле сада не превращается в поиск
   парков; продолжительность «около двух часов» не становится адресом.
3. По желанию `weather.py` запрашивает текущую погоду по огрублённым координатам.
4. `retrieval.py` фильтрует POI и ранжирует оставшиеся. Генератор получает до восьми карточек.
5. `generate.py` выбирает до трёх мест, валидирует идентификаторы и длительность, формирует
   объяснение из данных и проверяет идею действия модели либо использует шаблон.
6. `route.py` проверяет, можно ли объединить две–три рекомендации в один маршрут.
7. Ответ включает карточки, маршрут при наличии, источники, неопределённости и панель данных.
   UI хранит до пяти результатов в отдельной сессии. Повторный подбор — явное действие;
   TXT-скачивание использует уже готовый ответ и не вызывает модель.

| `core/place_search.py` | Ограниченный Photon-поиск короткого названия/адреса, валидация результата и кэш |

| `core/hours.py` | Подмножество OSM opening_hours, `open/closed/unknown` |
| `core/geo.py` | Расстояния, оценка ходьбы, радиус и бюджет |
| `core/retrieval.py` | Фильтры, BM25, контекст, до восьми кандидатов |
| `core/generate.py` | Выбор провайдера, POI, валидация, объяснения и идеи, локальный резервный режим |
| `core/server_config.py` | Единый провайдер и модель из окружения сервера |

| `core/weather.py` | Open-Meteo с безопасным отказом при недоступности |
| `cli.py`, `app/streamlit_app.py` | Две точки входа в общий конвейер |

## Данные

Основные поля POI: `id` вида `node/123`, `name` для ru/kk/en, `name_generated`, `lat/lon`,
`category`, `osm_subtype`, `tags`, `description`, `description_source`, `hours_raw`,
`wheelchair`, `indoor`, `website`, `phone`, `wikidata`, `source`, `evidence`.

`source` содержит OSM URL, лицензию и дату получения исходника. `evidence` связывает
поле с URL источника. Для новых Wikipedia-обогащений дополнительно сохраняются лицензия,
атрибуция, дата и описание сокращения текста. Существующие 14 выдержек имеют ссылки
на статьи, но не сохранённые ревизии.

Сбор и нормализация используют только стандартную библиотеку. Нормализатор проверяет
SHA-256 выбранного файла по метаданным. При отсутствии записи дата получения остаётся
неизвестной. Время нормализации не выдаётся за время сбора. Команда `make verify-data`
проверяет воспроизводимость основных OSM-полей без сети. Новая выгрузка может отличаться.

Дедупликация оставляет более полную запись при совпадении нормализованного русского
имени и расстоянии до 50 м. Это эвристика: соседние одноимённые объекты могут объединиться.
Безымянные площадки получают служебные названия. `indoor` иногда выводится из категории,
поэтому полнота этого поля не означает полевую проверку.

## Поиск и время

Текстовый старт — точка источника или центр территории, а не GPS и не проверенный вход.
Ручные координаты и выбранный ориентир имеют приоритет; итоговая точка видна пользователю.
Для Центрального парка сохранён центр из [Visit Astana](https://visitastana.kz/ru/about-city/what-to-see/tsentralnyy-park/).
Это отдельный источник ориентира, не новая запись в собранном датасете рекомендаций.

Внешний поиск использует Photon: до двух коротких названий/адресов после проверки
извлечения, `countrycode=KZ`, `bbox=71.20,50.95,71.80,51.35`, до восьми результатов.
Язык не задаётся: сервер возвращает свой язык по умолчанию и локальные имена OSM.
Конечные координаты должны быть конечными числами внутри bbox, OSM ID — корректным.
Явный город вне Астаны и вариантов её прежнего имени отбрасывается, даже внутри bbox.
Если город отсутствует, bbox не заменяет проверку соответствия имени и подтверждение.
OSM-ссылки строятся приложением по ID; URL и координаты модели не принимаются.

Кэш хранит только короткую поисковую фразу и результаты в памяти процесса: до 512 записей
на 24 часа. Лимиты — один старт HTTP-запроса в секунду и 30 в минуту на процесс;
очередь ждёт не больше секунды. Таймаут соединения/чтения — 3/12 секунд. Автоматических
повторов и массового сбора нет. Ошибка сервиса отличается от пустого успешного ответа.
`SERUEN_GEOCODING=0` отключает внешний поиск; `SERUEN_GEOCODER_URL` задаёт другой
Photon-сервер. Локальный режим не вызывает ни модель, ни геокодер.
Публичный Photon не даёт гарантии доступности или полного покрытия; для постоянной
нагрузки нужен подходящий сервер и общий лимитер. [Документация Photon](https://github.com/komoot/photon/blob/master/docs/api-v1.md).

Пешая скорость 4,2 км/ч, коэффициент к прямому расстоянию 1,3, запас пять минут.
Радиус выводится из бюджета за вычетом минимального планового посещения и запаса, с учётом возврата.
Короткий визит допускается, когда типичный не помещается: например, кафе и парк от десяти
минут, библиотека от пятнадцати, музей от тридцати. Работа требует не менее пятнадцати
минут; театральное посещение не сокращается до короткой остановки. Это оценки планирования,
а не гарантии фактической длительности услуги или спектакля.
Дорога не должна занимать больше 45% бюджета. Итоговый фильтр времени сохраняется
даже при автоматическом расширении радиуса в 1,8 раза.

Жёсткие ограничения: категория, избегаемые категории, помещение/улица при явном выборе,
доступность `wheelchair=yes` при требовании, исключение баров/пабов в детском сценарии,
расстояние, время и известное закрытие. При возможности рассчитываются прибытие и
достаточность времени до закрытия. Неизвестные часы остаются с предупреждением.

Скоринг складывает совпадение категории, нормированный BM25, близость, бонус открытого
места, погоду и контекст. Тишина и розетки являются пожеланиями, а не доказанными
характеристиками. В выводе не более двух мест одной категории и нет повторов названия.

Парсер часов поддерживает обычные дни недели, интервалы и переход через полночь.
Смежные и пересекающиеся интервалы объединяются; время до закрытия учитывает
следующий день, включая явно заданный выходной.
Неподдерживаемые правила, в том числе требующие календаря праздников `PH/SH`, дают
`unknown`. Источник часов не подтверждает, что заведение фактически работает сегодня.

Если `hours_raw` отсутствует, `indoor=false`, а подтип — `park`, `garden`, `playground`
или `memorial`, интерфейс может описывать неизвестность как условия доступа к месту,
а не часы работы заведения. Это узкая эвристика формулировки: машинный статус остаётся
`unknown`, ранжирование и фильтры не получают признака «открыто». Заполненное, но
неподдерживаемое расписание продолжает показываться как неизвестные часы.
`monument`, `artwork`, `viewpoint` и `attraction` исключены из этой эвристики: например,
Байтерек имеет `building=yes` в OSM, хотя нынешняя нормализация выводит `indoor=false`
из `monument`. Для выбранных подтипов размещение на улице выводится из категории,
а не проверяется на месте. Подпись не подтверждает свободный или круглосуточный доступ.

Текущий нормализованный `indoor` не хранит разницу между исходным тегом и выводом
из категории. `access`, `building`, `level`, `covered` и `barrier` в схему POI не входят;
`tags` — поисковые слова, а не все исходные OSM-теги. Поэтому отсутствие ограничения
в нормализованной карточке не означает разрешение входа. Исходный снимок сохраняет эти
поля; их явное перенесение с происхождением — отдельное улучшение схемы.

## Контракт генерации

Публичный интерфейс не выбирает провайдера и не принимает ключи посетителей.
`get_server_config()` читает `SERUEN_PROVIDER` (`openai`, `local`, `gemini`) и соответствующую
модель. Если провайдер отсутствует, приоритет: `OPENAI_API_KEY`, затем `GOOGLE_API_KEY`,
затем локальный режим. `SERUEN_DEMO=1` принудительно выбирает локальный режим.
`OPENAI_MODEL` и `GEMINI_MODEL` задаются явно; модель по умолчанию не придумана.
В CLI доступны `--provider` и `--model`; `--demo` отключает модель.

При выделении старта OpenAI получает текст с фильтрацией координат. При генерации
внешний провайдер получает текст, контекст и до восьми карточек
без отдельного поля координат пользователя. OpenAI использует один API key владельца
для всех посетителей. Сессии ответов и история интерфейса остаются раздельными.
Один запрос пользователя ограничен 2 000 символами до обращения к API.

JSON проверяется: объект ответа, список карточек, допустимый уникальный `poi_id`, типы
и диапазон минут. Уверенность ограничивается качеством данных. Неизвестные идентификаторы
отбрасываются. Пользователь видит объяснения из полей выбранного POI и контекста. Действие модели
проходит консервативный фильтр языка, формата и типовых неподтверждённых утверждений
о часах, стоимости, удобствах, доступности и безопасности. Принятая идея получает
условие «если условия на месте позволяют» и метку идеи. Это эвристика, а не полная
семантическая проверка. Отклонённое действие заменяется локальным шаблоном.

Если нет настроек, ответ невалиден или API недоступен, включается `retrieval-template`.
При отсутствии подходящих POI выводится честное объяснение, а не выдуманное место.
Внешний режим не переключается сам на другую модель. Подключение настраивает владелец. Отдельный реальный вызов OpenAI с моделью `gpt-6-luna` завершился успешно:
HTTP 200, `completed`, принят один POI из двух кандидатов, fallback отсутствует.
Офлайн-тесты протокола используют подменённые ответы. Детали: `docs/LIVE_VALIDATION.md`.

## Серверное подключение OpenAI

`openai_provider.py` читает `OPENAI_API_KEY` из окружения Python. Ключ не хранится в
сессии посетителя и не передаётся браузеру. Владелец сохраняет настройки в `.env` или
окружении размещения. После изменения настроек сервер нужно перезапустить.

Необязательный `OPENAI_REASONING_EFFORT` передаёт настройку `reasoning.effort`
поддерживающей её модели. Пустое значение не меняет запрос; неизвестное значение
отклоняется до обращения к API. Владелец проверяет поддержку выбранной моделью.

Генерация выполняется через `POST https://api.openai.com/v1/responses` с
`store: false`, `stream: false`, `max_output_tokens: 3000` и строгой JSON schema в
`text.format`. Принимается только ответ со статусом `completed` и JSON-объектом;
затем применяется общая проверка карточек. Отказ, незавершённый ответ, ошибка API,
некорректная структура или сеть приводят к локальному ответу. Автоматического повтора нет.
Сырые сообщения провайдера не показываются посетителям.
[Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create),
[Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Семафор допускает два одновременных обращения. Скользящее окно ограничивает запуск
запросов тридцатью за 60 секунд на процесс. При занятости модель не вызывается,
используется локальный ответ. Ограничения находятся в памяти процесса, сбрасываются
при перезапуске и не координируют несколько экземпляров. Публичное развёртывание требует общего ограничения нагрузки.

Команда владельца `make models` вызывает стандартный `GET /v1/models` и показывает
идентификаторы из `data[].id`. Наличие ID в каталоге не гарантирует совместимость
с Responses API и structured outputs. Модель выбирает владелец, генерация при просмотре
каталога не выполняется. `make gemini-models` обслуживает дополнительный Google-провайдер.

## Маршрут

Для максимум трёх карточек перебираются порядки и подмножества. Время каждого перехода
округляется вверх. Учитываются посещения, обратный путь и запас пять минут. При сокращении
посещений сохраняется минимальная длительность для категории, сокращение видно пользователю. Если нельзя собрать
хотя бы две остановки, маршрута нет. Карточки в таком случае остаются альтернативами.

По доступным расписаниям дополнительно проверяется время пребывания на каждой остановке.
Карта показывает последовательность точек, а не навигационный путь по улицам.
Для запроса поработать в одном месте маршрут по нескольким заведениям не строится,
если пользователь явно не попросил маршрут.

## Проверки

`make check`: офлайн-тесты, ruff и проверка датасета. Тесты охватывают часы, геометрию,
бюджет, фильтры, некорректные ответы модели, отказ API, происхождение данных,
разговорные формулировки старта, неоднозначность, чужие города и ограничения геосервиса,
а также интерактивные сценарии приложения. Сценарии с фиксированной датой и фактическими
выводами находятся в `docs/TEST_SCENARIOS.md`.
